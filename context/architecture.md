# Architecture Context

## Stack

| Layer     | Technology                        | Role                                                                 |
| --------- | ---------------------------------- | --------------------------------------------------------------------- |
| Framework | Next.js 16 (App Router) + TypeScript | Routing, Route Handlers, server/client components                  |
| UI        | Tailwind CSS + shadcn/ui           | Styling and base component primitives                                 |
| Animation | Motion (`motion/react`)            | Leaderboard bar transitions, re-ordering, entry/exit animations       |
| Data (live) | SWR + ETag conditional requests   | Client-side polling of `/api/leaderboard`/`/api/session-info`, with a `304 Not Modified` short-circuit when nothing changed since the last poll — see Invariant #8 |
| Database  | Neon (Postgres)                    | Reserved for future features (session history, multi-session support) — not used by the current live leaderboard path |
| ORM       | Drizzle                            | Same status as above — scaffolded, not wired into any feature yet     |
| Deploy    | Vercel                             | Hosting; drives the polling-over-streaming decision below             |

## System Boundaries

- `app/` — routes only. `app/page.tsx` renders the dashboard.
  Two Route Handlers are the only places that call the mobile app,
  each proxying one upstream endpoint:
  - `app/api/leaderboard/route.ts` calls `GET /evaluations` (URL
    from `EVALUATIONS_API_URL`), validates
    (`lib/evaluation-validate.ts`), and returns
    `{ evaluations: Evaluation[] }` — the raw, validated list, not
    pre-aggregated rankings. That's a deliberate deviation from
    the original plan (aggregating server-side): the detail
    dialogs (per-juror, per-project breakdowns) need the raw
    per-evaluation records anyway, so aggregation happens once,
    client-side, in `lib/evaluation-aggregate.ts` — computing it
    twice (server for a summary, client for detail) would just be
    duplicated logic for no real benefit at this data size (~2400
    records max).
  - `app/api/session-info/route.ts` calls `GET /health` (URL from
    `HEALTH_API_URL`), validates
    (`lib/session-info-validate.ts`), and returns
    `{ jurorCount, projectCount }` — the live juror/project roster
    size. This is the fix for "what if a juror or project is added
    mid-session": the roster is polled (every 30s, `Dashboard`),
    not baked into a build. See Session Notes for why this exists.
  - `app/api/acces/route.ts` is unrelated to the mobile app — it
    validates a submitted PIN against `DASHBOARD_PIN` and sets the
    access cookie. See Auth and Access Model.
- `proxy.ts` (project root — Next.js 16's renamed Middleware, not
  `middleware.ts`) gates the dashboard page behind that PIN. See
  Auth and Access Model for what it does and doesn't cover.
- `components/` — presentational UI. `components/ui/` holds
  shadcn/Base UI-generated (or hand-built-to-match, see
  `dialog.tsx`) primitives (protected, see `ai-workflow-rules.md`);
  leaderboard-specific components (animated bars, juror rows,
  detail dialogs) live alongside, built on top of those
  primitives.
- `lib/` — non-UI logic: `evaluation-aggregate.ts` (the real
  ranking/aggregation functions — running average, completion
  counts, per-criterion breakdowns; used both by the live app and,
  during dev, against `mock-evaluations.ts`'s simulated stream).
  Roster size (`jurorCount`/`projectCount`) and the
  `J1..Jn`/`P1..Pn` code arrays are **not** module constants here
  — they're generated by `generateJurorCodes`/`generateProjectCodes`
  from counts the caller supplies, because the true count is a
  runtime value from `/api/session-info`, not a build-time
  constant (see System Boundaries and Session Notes).
  `DEFAULT_JUROR_COUNT`/`DEFAULT_PROJECT_COUNT` (env-configurable)
  exist only as a fallback for before the first successful
  `/health` fetch. `evaluation-validate.ts` and
  `session-info-validate.ts` are boundary validation for the two
  upstream responses. `mock-evaluations.ts` is dev-only simulation,
  not used once real data is wired up. Pure functions here are
  testable without a network call or a browser.
- `db/` — Drizzle schema and Neon client. Currently unused by any
  shipped feature — see Invariants. Exists so future
  session-history work has a place to start without restructuring
  the app.

## Storage Model

- **Live leaderboard data**: not persisted anywhere in this app.
  Every request to `/api/leaderboard` fetches fresh from the
  mobile app's `GET /evaluations`, computes rankings in memory,
  and returns them. The mobile app's own database is the sole
  source of truth for evaluation data.
- **Neon (via Drizzle)**: reserved for future, not-yet-built
  features — e.g. persisting session snapshots over time, or
  supporting more than one award session/event. No tables exist
  yet; do not add speculative schema before a concrete feature
  needs it.

## Auth and Access Model

- **The dashboard page is gated behind a single shared PIN**
  (`DASHBOARD_PIN`), added 2026-07-16 after a cost discussion:
  every extra tab left open by an unintended viewer adds to
  Vercel's fast-data-transfer usage (see progress-tracker.md).
  `proxy.ts` (Next.js 16's renamed Middleware) checks a cookie set
  by `app/api/acces/route.ts` on a correct PIN submission
  (`app/acces/page.tsx`); no cookie → redirect to `/acces`. Same
  security bar as the mobile app's own admin PIN — **a deterrent,
  not real security** (single shared secret, no rate limiting, no
  per-person accounts).
- **Deliberately API-scoped, not app-wide**: `proxy.ts`'s matcher
  only covers `/`. `/api/leaderboard` and `/api/session-info`
  remain callable without the PIN — the user chose this
  explicitly, aware it means the PIN doesn't fully bound API-level
  cost exposure (someone could still call the API directly without
  ever loading the gated page). It does stop the realistic case
  this was built for: a casual/unintended viewer finding the URL
  and leaving a tab open.
- No ownership/multi-tenancy model — one shared live session per
  deployment, matching the mobile app's single-event scope.

## Invariants

1. This app never writes evaluation data. All scoring mutations
   happen in the mobile app; every Route Handler here is
   read-only relative to evaluations.
2. No direct database coupling with the mobile app. The only
   integration point is its `GET /evaluations` API — no shared
   Drizzle schema, no shared Neon instance for evaluation data.
3. Real-time updates use polling (server-side fetch of the mobile
   API + client-side SWR polling of this app's own route), not
   SSE/websockets/long-lived connections — Vercel's serverless
   model doesn't suit holding those open.
4. The Neon/Drizzle scaffolding must never become a second source
   of truth for live evaluation or leaderboard data. If a future
   feature (e.g. session history) starts reading Neon on the live
   leaderboard's request path instead of the mobile API, that's an
   architecture violation — flag it and update this doc first.
5. The all-projects standings/completion views must not render all
   ~200 projects as simultaneously animated bars — resolved via
   search (`board-search.tsx`) + a 30-row render cap applied
   *after* ranking, not a hard display cap. Don't regress this by
   removing the cap "to show more."
6. Project codes from the mobile API are **not zero-padded**
   ("P13", "P7", "P200", not "P013"/"P007") — confirmed against
   real data 2026-07-16. `generateProjectCodes` in
   `lib/evaluation-aggregate.ts` must stay consistent with this or
   every aggregate lookup silently breaks (this happened once
   already during initial real-data testing).
7. The juror/project roster size must never be hardcoded as a
   module constant read directly by components — it's a runtime
   value from `/api/session-info` (`Dashboard` fetches it and
   threads `jurorCount`/`projectCount`/`jurorCodes`/`projectCodes`
   down as props/params). `DEFAULT_JUROR_COUNT`/
   `DEFAULT_PROJECT_COUNT` exist only as a pre-first-fetch/fetch-
   failure fallback, not a substitute for the live value.
8. Both proxy routes (`/api/leaderboard`, `/api/session-info`)
   must support conditional requests (`ETag`/`If-None-Match` →
   `304`) — this is what makes a 3s poll interval affordable on
   Vercel's Fast Data Transfer cap, not the interval length itself.
   `lib/etag.ts` (server) / `lib/etag-fetcher.ts` (client) implement
   this; any new polling route should reuse the same pattern rather
   than re-sending a full payload on every poll. Verified
   end-to-end 2026-07-16: a real 28KB `/api/leaderboard` response
   became a 0-byte `304` on the very next poll with an unchanged
   `If-None-Match`.
